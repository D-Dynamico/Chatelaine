## Surprises

- **The rules file was the wrong one (#5).** CLAUDE.md, which every session loads first,
  said the delay is "clamped" and that "every API" accepts it. Taken literally, a clamp
  turns `delay=10001` into 10000 and returns 200, and the `/health` route would honour a
  delay. That code would have looked compliant against the file most likely to be read,
  while failing §9, the simulation tests and a Stage 1 exit criterion. A one-word
  ambiguity in the always-loaded summary outranks a correct detail doc in practice, so the
  summary now uses the same words as §9.
- **A correct-looking interceptor chain could never report a timeout (#16).** With the
  timeout interceptor outside the request log, a timeout unsubscribes from the log's stream
  rather than erroring through it. The log's `finalize` then sees neither a response nor an
  error and records `cancelled`. Every unit test of the log in isolation would pass; only
  the order was wrong. The new `requestLogInterceptor` test runs through the full
  registered chain so it goes red if the order regresses, and `errorInterceptor` gets a
  test proving it passes an existing `CLIENT_TIMEOUT` `ApiError` through unchanged.

- **npm 11.5 strips platform bindings from the lockfile on a second install.** Found while
  adding zod: the lockfile lost 512 lines, all 26 optional native bindings for rolldown
  (vitest's bundler) and lightningcss, including the Windows one in use. Reproduced from a
  clean state: a fresh `npm install` writes all 26, and the very next `npm install`, even
  with no change, removes them. The entries are marked both `optional` and `peer`, which
  is the combination that gets pruned. Nothing fails locally because `node_modules`
  already holds the binding, so this would first have shown up as a broken test gate on
  Linux CI or a failed Render build in Stage 7. Fixed with a procedure (edit `package.json`,
  delete `node_modules` and the lockfile, install once; WORKFLOWS §28) and a guard,
  `scripts/check-lockfile.js`, run by `npm run lint`. The guard was shown to fail on the
  stripped lockfile (26 missing, exit 1) and pass on a fresh one. A fresh resolve
  reproduced the 1.1 lockfile byte for byte, so that commit was sound. Committed on its
  own, ahead of 1.2, because it is a separate fix with its own reason.

## Stage 1 substeps

Each is one commit, and tests land in the same commit as the unit. A commit is made when
the change is green on every gate, can be described in one sentence with a reason, and can
be reverted on its own. A first draft of 14 substeps was merged into 8 with DJK, because
several pieces (constants with no consumer, a `validate` middleware nothing called) could
not justify themselves as separate commits. Expect about 8 commits per stage.

- [x] 1.1 **Scaffold the API package with its quality gates.** `package.json` (ESM,
      `engines >=24`, §28 scripts), strict `NodeNext` tsconfigs, ESLint with
      typescript-eslint, Prettier, Vitest; root `.nvmrc` and `.gitattributes`
      (`eol=lf`, so Prettier's check passes on Windows checkouts). The clock in `lib/` is
      the first real unit, so the gates check something genuine rather than a placeholder.
      *Done.* Installed: typescript 6.0.3, eslint 10.12, typescript-eslint 8.71, prettier
      3.9, vitest 5.0.3, tsx 4.23, rimraf 6.1, `@types/node` 24 (all D29). Lint, format,
      typecheck, 4 tests and build green on Node 26.7. Lint proven able to fail: a probe
      file with `any`, `console.log` and `!` produced four errors. Notes: `dev`, `start`
