# 2026-10-10: Stage 6 (latency lab)

## Scope

Stage 6 from §31: the lab drawer with presets, fail-next, the three loading strategies, the
client timeout, "Reload dashboard" with cancellation, and the request timeline.

Exit criteria (§31): switching strategy visibly changes the timeline; a double "Reload
dashboard" shows cancelled bars; a 10 s delay with a 5 s timeout shows the timeout state; the
timeline is usable by keyboard; reduced motion is respected.

## Proposed decisions (for DJK)

1. **The drawer is one non-modal panel, not a Material sidenav or bottom sheet.** The point
   of the lab is to watch the dashboard load while the timeline draws, so a backdrop that
   dims or blocks the page would defeat it. It is an `<aside>` the shell shows on the right
   (a bottom sheet under 720 px, by CSS alone), with no backdrop. Escape closes it, focus
   moves in when it opens and returns to the "Timeline" button when it closes, and the
   page behind stays usable. It is loaded with `@defer` on first open, so the sliders, the
   timeline and their styles stay out of the shell chunk until someone asks for them.
   Alternatives: `MatSidenav` (modal over the page, or pushes the content aside) and
   `MatBottomSheet` (always modal).
2. **A strategy applies at the next load, not at once.** Choosing "All at once" does not
   reload by itself; "Reload dashboard" does. That matches the §38 demo script ("switch to
   All at once, reload"), keeps cause and effect visible, and avoids a surprise reload while
   someone is dragging a slider.
3. **What each strategy does to the three panels** (the dashboard load is profile, summary
   and the records page for the current URL):
   - **Independent** (today's behaviour): three streams, each renders as it arrives.
   - **All at once:** `forkJoin`. All three panels stay on their skeletons until the slowest
     finishes. If any fails, all three show their error state with that failure, and "Try
     again" on any of them reloads all three, because they are one unit.
   - **One after another:** `concat`: profile, then summary, then records. A failed step does
     not stop the later ones (each request becomes a state, so the chain continues): the
     point is the waiting, not the error handling.
   Paging, sorting or filtering the records table afterwards reloads only the table, under
   every strategy: a strategy describes how the page loads, not each later interaction.
4. **Presets are four functions over the sliders, not state.** "Instant" 0 everywhere;
   "Realistic" 300 / 900 / 1600 / 500 (profile, summary, records, admin), as §19 says;
   "Slow network" 2500 / 3200 / 4000 / 3000; "Staggered" 3000 / 1500 / 500 and admin 500.
   The active preset is whichever one the current sliders equal (none, once a slider is
   moved), so there is nothing to keep in sync.
5. **Pending bars grow live only while something is pending, and not at all under
   `prefers-reduced-motion`.** The clock that grows them is a `requestAnimationFrame` loop
   that runs only while an entry is pending and stops itself. Under reduced motion the
   pending bar is drawn at a fixed length with the word "Pending", and snaps to its true
   length when the request ends. §26 says motion is used on the timeline and nowhere else;
   this keeps that promise for people who ask for less.
6. **"Reload dashboard" is shown only while the dashboard is open.** Elsewhere nothing
   listens to it, so a button that does nothing would be a trap. It is hidden off that
   route, not disabled.

No new dependencies: `mat-slider`, `mat-button-toggle` and `mat-slide-toggle` are in the
Angular Material already installed.

## Surprises

- **Full test runs went unreliable again, and it is the machine.** With about 1 GB of 5.8 GB
  free, whole-suite runs failed in two ways that moved around between runs: the first test
  of some file timing out just over 5 s (a different file each time), and a run in which 19
  files failed because Angular's temporary test bundle had been deleted while they ran.
  Every failing test passes alone and in smaller runs, no assertion was touched, and no
  stray `ng test` process was running (the old `ng serve` and API watchers from 8 October
  still are). For this stage the suite is run as four sequential groups (`core`;
  `shared`, `layout` and the two root specs; `features/admin`; `features/dashboard`,
  `auth` and `latency-lab`), whose counts add up to the full 276. The CI run at Stage 7
  has more memory, but a worker cap in a `vitest` runner config is worth considering then.

- **The lab overflowed its drawer at 360 px, twice (6.5).** jsdom does no layout, so no test
  could see it. First, the sliders had `width: 100%; margin: 0`, so their thumbs stuck out of
  the drawer by half a thumb at each end (Material expects a side margin there). Second,
  with real data the rows overflowed: every grid in the lab (the panel, its sections, the
  timeline, each row) had a plain `1fr` or `auto` column, which grows to its widest child,
  here an unbroken request path such as `GET /records?page=1&pageSize=10&sort=...`, 520 px
  against a 298 px drawer. `minmax(0, 1fr)` on each fixed it, the same cause as the
  dashboard's 841 px page in Stage 4. My first measurement used the first row, a short
  `/me`, and looked fine; the long row only showed when I measured the whole list.
- **A hidden window cannot show the thing this stage is about (6.5).** Chrome pauses
  `requestAnimationFrame` and throttles timers in a hidden window, so live bar growth and real
  key presses cannot be checked there. The checks that need no frames were driven through
  page script (strategy order from the browser's resource timings, rows read from the DOM),
  and the rest is covered by tests with fake timers. Worth doing once by hand in a visible
  window before the demo recording.
- **The axis makes new bars tiny after a long session (6.5, by design).** §19 starts the axis
  at the first request in view, so after a minute of use a fresh load's bars are 1 to 6 % of
  the width. "Clear" fixes it and the demo script now says to press it first. Auto-clearing on
  "Reload dashboard" was rejected: a second press would wipe the first attempt's cancelled
  bars, which are the whole point of pressing twice.
- **A template reference on a Material button is the component, not the element (6.4).**
  `viewChild('timelineButton')` on `<button mat-button #timelineButton>` returned the
  `MatButton` instance, so `.nativeElement.focus()` threw "Cannot read properties of
  undefined" the first time Escape closed the drawer. The Escape test caught it, because it
  asserts where focus went. It needs `read: ElementRef` (and an explicit generic, or the
  result is `any`).
