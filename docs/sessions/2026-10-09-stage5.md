# 2026-10-09: Stage 5 (admin)

## Scope

Stage 5 from §31: lazy admin route; users table with URL-backed query state; create and
edit dialog with async userId check; delete dialog with record count and "Disable
instead"; self-row protections.

Exit criteria (§31): full create, edit, disable, delete round trip on the deployed-like
setup; `USER_EXISTS` and `SELF_ACTION` (forced by calling the API directly) each shown in
the UI; admin chunk appears as a separate file in `ng build` output.

The lazy route and an empty `UsersPage` already exist from Stage 3, so the chunk is there;
this stage fills it.

## Decisions (all four approved by DJK, with details)

- **1. Approved.** §25 gets "Disable user" / "User disabled" and "Enable user" / "User
  enabled". The disable confirm states the effect: "Disable Riya Sharma? They'll lose
  access on their next action. You can enable them again later." (DJK's wording used
  "She'll" and "her" for Riya; the sentence is a template for any user, so it uses
  they/them, which is right for everyone.) Checked against the API: `resolveSession`
  reloads the user on every request and refuses a disabled one, so "next action" is true.
  "Disable instead" in the delete dialog counts as confirmed, so no second dialog.
- **2. Approved.** §31's Stage 5 exit criterion is reworded: `SELF_ACTION` is proved by the
  API tests plus a component test showing the dialog displays the 409; `USER_EXISTS` is
  shown in the real UI through the console race. A 409 `USER_EXISTS` sets the userId
  field to "Already taken".
- **3. Approved, as a hint.** The async validator returns null when the check fails, and
  the field shows "Couldn't check availability" separately, outside validation. Only a
  404 means available; 401, 403, 5xx and `CLIENT_TIMEOUT` all mean "couldn't check".
  Earlier checks are cancelled by `switchMap`. Tests for 404, 200, 503 and timeout. §38
  notes that "Fail next" on the admin group can be taken by the availability check.
- **4. Approved.** The session is updated from the PATCH response, not the form values,
  through one `SessionStore` method that only accepts a `UserView` with the current
  session's userId. `SessionStore` stays the single writer; §15 says so.

The original proposals:

1. **Disable and enable from the row menu.** §25 has "Disable user" / "User disabled" but
   nothing for the way back. Proposal: the row menu offers "Disable user" behind a short
   confirm dialog ("Disable Riya Sharma? They won't be able to sign in until you enable
   them again."), and "Enable user" with no confirm, since it only restores access.
   Snackbars "User disabled" and "User enabled". §25 gets the "Enable user" row. Status
   can also be changed in the edit dialog, as §20 says.
2. **How `SELF_ACTION` is shown in the UI when the UI never sends it.** The own row has
   Delete, role change and Disable unavailable, so a real click cannot produce it.
   Proposal: in the browser exit check, the refusal is forced by calling the API directly
   from the console with Meera's token (proving the server rule), and the dialog's
   handling of a 409 `SELF_ACTION` is proved by a component test that answers the save
   with that error through `HttpTestingController`. `USER_EXISTS` is shown in the real
   UI: open Create, type a free userId (shows "Available"), create that user from the
   console, then submit; the dialog shows "That user ID is already taken. Choose another
   one." under the field. No app code is added for testing.
3. **The availability check goes through the latency lab like every admin request.** An
   admin delay makes "Checking" visible, which is honest. If the check itself fails (an
   armed failure, a timeout, a 5xx), the field says "Couldn't check availability" and
   does not block submit; the server's 409 remains the real guard. The alternative,
   skipping simulation for it, would hide the async state the brief asks to show.
4. **Editing your own row updates the session.** If Meera changes her own display name,
   the account menu and dashboard card should not keep the old one until refresh. After a
   successful save of the signed-in user, `SessionStore` takes the returned `UserView`.

No new dependencies: dialog, menu, tooltip and button toggle are in Angular Material,
already installed, and all of it lands in the lazy admin chunk.

## Surprises

- **A disabled menu item still clicked through (5.3).** Material's `disabledInteractive`
  keeps a disabled item focusable so a tooltip can explain it, and sets `aria-disabled`,
  but the click still reaches the `(click)` handler. The first table test clicked Delete
  on Meera's own row and the `remove` output fired. Without the test the page would have
  opened the delete dialog for the signed-in admin (the API would still refuse with
  `SELF_ACTION`, but the UI would have offered what it claims not to). The handlers now
  check the row themselves.

- **The suite went unreliable when memory ran out, and one spec leaked a timer.** With
  0.6 of 5.8 GB free, full runs failed in three different ways: first tests timing out
  just over 5 s, whole suites failing with ENOENT on Angular's temporary test bundle
  (the run before it was killed), and a run that passed all 212 tests but exited 1
  because `guards.spec.ts` navigated to the real pages with no HTTP backend, so a
  request was left waiting and its 12 s client timeout fired as an unhandled error
  during a later test. The spec now uses `provideTestHttp([])` (no interceptors, so no
  timer). The memory is an environment problem, not a code one: no assertion was
  changed, and each failing test passes alone.
