# 2026-10-08: Stage 4 (dashboard)

## Scope

Stage 4 from §31: `toLoadState`; access card, summary strip, records table with
server-side paging, sort and filter; role-dependent columns; expandable internal note for
admins; mobile list layout.

Exit criteria (§31): each panel loads, empties and errors on its own (using `delay` and
`fail`); General and Admin views differ exactly as §5 says; usable at 360 px; no skeleton
flash on paging.

## Decisions (approved by DJK, with details)

- **1. Approved.** Correction to the Stage 3 note: its "Next session" put the
  `reloadRequested` reaction in Stage 4; it belongs to Stage 6 with the strategies.
- **2. Approved.** The URL-state helper lives in `core/` (admin reuses it in Stage 5), and:
  drops `access` for General Users before any request, so a shared admin link never
  causes a 403; parses every param defensively, so an unknown or invalid value falls back
  to its default and is never sent to the API; resets `page` to 1 when any filter
  changes; uses `replaceUrl` for search keystrokes so Back is not flooded. Tests for the
  General User strip and the invalid-param fallback.
- **3. Approved, amended.** `isRefreshing` goes on both `loaded` and `empty`, so a refresh
  from an empty result does not show the skeleton either. A refresh that fails replaces
  the view with the error state: stale rows that no longer match the URL are not kept.
  §18 and D22 say so.
- **4. Approved, amended.** Failures are forced by writing a fail-next flag into the saved
  latency settings and reloading, so the request goes through the real simulation
  interceptor and the API's `SIMULATED_FAILURE`. That required reversing a Stage 3
  decision (fail-next was deliberately not persisted, and a test asserted it). DJK chose
  to persist armed flags: a flag is saved until a request takes it, then cleared. New
  substep 4.0. The console cannot import `STORAGE_KEYS`, so the snippet uses its value
  `'chatelaine.latency'`; the exact snippet is recorded at the exit check.

The original proposals:

1. **Loading strategies and "Reload dashboard" stay in Stage 6**, as §31 lists them there.
   Stage 4 loads the three panels independently (the default strategy), and
   `DashboardDataService` is shaped so that Stage 6 can add `forkJoin` and `concat` next to
   it. This corrects the Stage 3 note, which put the `reloadRequested` reaction in Stage 4.
2. **The records query lives in the URL** (`?q=&status=&priority=&access=&page=&sort=&order=`),
   as §20 already requires for the admin users table. A refresh or a shared link then
   keeps the view, and Stage 5 reuses the same small helper instead of writing a second
   one. The alternative is component signals only (simpler, but the view is lost on
   refresh).
3. **"Keep previous data while refreshing" (§18)** needs one addition to `LoadState`: the
   `loaded` state carries `isRefreshing`. `toLoadState` emits `loading` only when there is
   no data yet; later requests keep the last data with `isRefreshing: true`, which drives
   the thin progress bar on the panel edge. This keeps one type for every panel (D22)
   rather than a second flag beside it. §18 gets the updated type.
4. **Driving `delay` and `fail` in the browser before the lab exists:** delays through the
   persisted latency settings in `sessionStorage` (the store reads them on load), and
   `fail=true` by appending it to one endpoint's requests from the browser console. No
   app code is added for testing. The lab UI arrives in Stage 6.

No new dependencies: table, paginator, sort and expansion are in Angular Material, which is
already installed. All of it lands in the lazy dashboard chunk, so the initial bundle does
not grow (§14).

## Stage 4 substeps

- [x] 4.0 **Keep an armed failure until a request takes it.** `LatencySettingsStore`
      persists armed fail-next flags with the other settings; `takeFailure` clears the
      flag and the saved copy. The Stage 3 test that asserted the opposite changes, because
      the decision changed (decision 4), not to make it pass. §15 updated.
      *Done.* `armedFailures` joined `LatencySettings` and is parsed back like the rest
      (unknown groups and duplicates dropped). The store now saves synchronously on every
      change instead of from an `effect`: an effect writes later, so a flag taken just
      before the page unloads could stay saved and fail the next load too. Verified: 112
      tests. Mutation checks, each killed: clearing a taken flag in memory only (the
      "taken, then reloaded" test fails), and not parsing the saved list back.
- [x] 4.1 **Load state and the dashboard's data.** `LoadState<T>` and `toLoadState` in
      `shared/load-state/` (with `isRefreshing`, decision 3); records models mirroring
      §11 (enums, General and Admin item shapes, query, page, summary);
      `DashboardDataService` provided on the dashboard route, with `profile`, `summary` and
      `records(query)` streams, each with its own retry `Subject` feeding `switchMap`, so
      "Try again" twice cancels the first attempt. Tests: `toLoadState` (loading, loaded,
      empty, error, refresh keeps data) and the service with `HttpTestingController`
      (three independent requests, a failing one does not affect the others, retry
      cancels).
      *Done, with the URL-state helper from 4.5 pulled forward,* because the records
      stream is driven by the parsed query and its tests belong with it. `LoadState`'s
      error is a `LoadFailure` (`status`, `code`, `message`) declared in `shared/`, since
      `shared/` cannot import `ApiError`; `ApiError` fits it structurally, and anything
      else becomes a plain-words `UNKNOWN` failure. Refresh behaviour is a separate
      operator, `keepDataWhileRefreshing()`, after the `switchMap` (§18, D22 updated).
      `core/routing/url-query.ts`: each param is a small codec (`optionalChoice`,
      `choice`, `searchText`, `pageNumber`) with a fallback; `injectUrlQuery(shape,
      'page')` gives a `values` signal and `update(change, { isTyping })`. Any change
      other than the page resets it to 1, typing uses `replaceUrl`, and every write sets
      all of the shape's keys, so invalid or unknown params disappear from the URL on the
      next change. `features/dashboard/records-query.ts` holds the records shape (the API's
      limits: `q` up to 60, page up to 100000) and `toRecordQuery(state, isAdmin)`, which

      `keepDataWhileRefreshing`, retry with `mergeMap` instead of `switchMap` (the first

## Surprises

- **Making the dashboard lazy made two route tests flaky (4.3).** The boot test and the
  first guard test failed in two of three full runs, each passing alone. In the test
  environment a lazy module is compiled on its first import; under a full parallel run
  that took longer than the 5 s test timeout, or the 1 s `vi.waitFor` default. Fixed
  without touching an assertion: `testing/lazy-routes.ts` imports every lazy page once in
  `beforeAll` with a 60 s allowance, so each test's time measures the router, not the
  compiler. Four full runs green afterwards, and the boot test's mutant is still killed.
