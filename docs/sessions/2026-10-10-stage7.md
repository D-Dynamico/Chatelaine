## Proposed decisions (for DJK)

1. **Vercel, not Netlify.** §29 lists Vercel first and its config (`vercel.json` with one
   rewrite to `/index.html`) is one file. Netlify would be a `_redirects` file and nothing
   else changes. Say so if you would rather use Netlify.
2. **No Playwright.** D25 made end-to-end tests a stretch goal needing your approval as a new
   dependency. Every exit check so far was done in the real browser and recorded, the demo
   script (§38) covers the same path by hand, and a browser-test dependency in CI is more
   moving parts than the last stage has time for. It goes in the README's future scope.
3. **"Last signed in" gets fixed with a small API change: a `previousLoginAt` field.** Today
   `/me` can only show the current session ("just now", always), because the API overwrites
   `lastLoginAt` at the sign-in that returns it. An evaluator will read that as a bug.
   Proposal: login stores the old `lastLoginAt` as `previousLoginAt` before overwriting it,
   `UserView` gains `previousLoginAt: string | null`, the access card shows it ("Last
   signed in 23 hours ago", or "First sign-in" when null), and the shared contract suite
   covers it on all three adapters. This is an API contract change, so it needs your
   approval and a D-entry. The cheaper alternative changes no contract: relabel the card
   "Signed in just now", which is true but tells the user nothing.
4. **No worker cap or runner config for the web tests.** The Stage 6 flakiness was this
   machine's memory (0.6 to 1.1 GB free), not the suite. GitHub's runners have 16 GB. If CI
   shows first-test timeouts, a `vitest` runner config with a worker cap is the fix, and it
   would be recorded then.
5. **The `req.ip` check takes two deploys.** A one-line temporary log goes in the API (a
   `logger.info({ ip: req.ip, forwarded: req.get('x-forwarded-for') })` on `/health`), you
   deploy it and open the health URL from your own machine, and we compare what it logged
   with your real IP. Then the line is removed and deployed again. There is no way to learn
   Render's proxy behaviour without Render.

## Surprises

- **`TRUST_PROXY=1` was wrong on Render, and only Render could say so (7.8).** The plan, §29
  and `.env.example` all said one proxy sits in front of the app. A real request logged on the
  live service had `X-Forwarded-For: <client>, <Cloudflare edge>, <Render internal>`, a socket
  address of `::1`, and with `TRUST_PROXY=1` `req.ip` came out as `10.199.44.5`, Render's
  internal address. Every visitor would have shared one login rate-limit bucket (ten attempts
  per fifteen minutes in total, so the demo would lock itself out). Three hops is right: Express
  counts the socket as hop 0, so the client is the fourth address from the right. The fake
  address I put in the header myself (`198.51.100.7`) showed up first in the chain, which is
  also why the count must be exact: too low trusts a header the client wrote. Two earlier
  attempts at the check read Render's own health checks (`render-health-check: 1`, from inside
  its network), which say nothing; the log line was changed to fire only for requests that carry
  `X-Forwarded-For`, and to put its answer in the message. `render.yaml`, `.env.example`, §29
  and API §8 now say 3.
